# GetYourFit live-scope acceptance contract

Journey assertions use public browser and API behavior observed against the local production service, plus the written requirements in `docs/requirements.md`. The model-download guard shares the pinned model identity from `shared/classification.ts`; its exception is defined below. Endpoint and DTO shapes below are the observed transport projection; the behavioral expectations remain governed by the requirements. The API contract was traced through signup, session, wardrobe listing, photo retrieval, fact correction, removal and outfit requests in a real browser.

## Production process

`npm run build` produces the release build. `npm start` serves that build and its API using `HOST`, `PORT`, `APP_URL`, `GYF_DATA_DIR`, `DATABASE_URL` and `BETTER_AUTH_SECRET`; the production service additionally reads `BETTER_AUTH_URL`, which the runner also sets. The runner generates a disposable random 64 character secret for each run and never persists it. Storage for a run must stay inside `GYF_DATA_DIR`.

The main runner supplies a disposable database: a temporary `GYF_DATA_DIR` by default, or a disposable Postgres `DATABASE_URL` with `GYF_ACCEPTANCE_BACKEND=postgres`. The application has no mail transport, and no prerequisite external identity or email provider is needed. The no-mail signup observations below describe the product: email confirmation is off.

## Browser journey

Visible text on public, sign-in, signup, and signed-in wardrobe/account pages meets WCAG AA contrast at 390px, 768px, and 1440px. The contrast case checks the production build with axe-core's `color-contrast` rule, requires at least one evaluated text node per scan, and fails on violations or checks requiring manual review. Normal text requires 4.5:1; large text requires 3:1. The public case also scans axe WCAG 2 A/AA and 2.1 A/AA rules and checks the account-entry focus/status behaviors below. It does not establish full WCAG or assistive-technology conformance.

A clean landing page works without the account API and has a main region, a labeled complete example with three real self-hosted photographs, its reasons, illustrative-facts disclosure, honest server-storage privacy copy, and a Use my own clothes action with at least a 44px touch area. Use my own clothes opens signup. Build my wardrobe opens account entry with an allowlisted return to the signed-in planner. The public illustration is static, with no interactive look choices. Planning, recommendations, photo and save workflows require a server-validated session. Direct private URLs, forged client state and expired sessions cannot bypass account entry. It has no account form or release jargon. Its public module response is compressed when the browser accepts gzip. At 390px, 768px, and 1440px, it has no horizontal overflow. Following Use my own clothes by keyboard opens signup. Loading announces status, the first field receives focus, and password requirements are associated with the input. Inputs use at least 16px text. A failed Enter submission retains values and focuses its error; retrying by Enter creates an account and focuses its empty wardrobe. A separate touch-enabled phone journey submits by tap. Visible public, signup, wardrobe/account, garment-consent, saved-garment/outfit, and refreshed screens must not claim that saved account photos or facts remain on the visitor's device, phone, or browser. Consent and review distinguish on-device recognition from server storage using the [photo recognition privacy contract](../../docs/photo-recognition.md). Name, email and password fields have labels. Empty Name refuses form submission; the checker then supplies a synthetic name. A visible 18+ confirmation checkbox is required, and the browser refuses submission while it is unchecked. Successful signup returns 2xx, sets a private session cookie and closes the signup form before garment controls are checked. Creating an account makes the garment upload available without mail. A labeled Garment photo file control, an initially unchecked photo-processing consent checkbox, and a Save garment/Add garment/Upload photo action let the person add the licensed shirt fixture. An optional Review photo action may precede saving. The wearer confirms the shirt's name, category, color, size, fit, available status, weather, dress codes and ownership before saving. The checker uses the synthetic facts Acceptance beige shirt, top, beige, size M, fits, available, mild weather and smart-casual dress code. The browser then requests an outfit with known weather and dress code; because this journey owns only one shirt, it must receive one question or an abstention and no complete outfit. Refresh preserves the session and the exact saved photo: the rendered image source remains the upload response's `photoUrl`, the image decodes at its natural size, and its rendered pixels match before and after refresh. The journey has no browser errors, unexpected external requests, or horizontal overflow at 320/390/768/1440 pixels.

The browser network guard aborts every off-origin request. Only payload-free GET downloads of the pinned model assets and their validated redirects, recognized by [model-download.mjs](src/model-download.mjs), are exempt from the unexpected-request failure. Photo, account, and garment-fact egress remains forbidden. The blocked model downloads must leave an unavailable interpretation and allow manual saving. This deterministic journey does not prove successful inference; [recognition verification](../../docs/photo-recognition.md#verify-recognition) owns that proof.

All API requests use synthetic accounts and the local app Origin. JSON responses declare `application/json`. Signup creates a usable private session without real mail. Session cookies are HttpOnly and SameSite Lax or Strict. HTTPS deployment must additionally use Secure cookies; this HTTP loopback harness does not prove that deployment property.

| Interface | Request | Observable response |
| --- | --- | --- |
| `POST /api/auth/sign-up/email` | `{name,email,password,adultConfirmed:true,callbackURL}` with generated credentials | 2xx JSON, private session cookie; account usable immediately |
| Rejected signup | Same valid fields with `adultConfirmed:false` or omitted | 4xx, no session cookie; follow-up login cannot use the rejected account |
| `POST /api/auth/sign-in/email` | `{email,password,rememberMe:false}` | 2xx JSON for valid credentials; same 401 status and JSON body for wrong password and unknown email; neither creates a session |
| `GET /api/session` | Session cookie | `{signedIn:true,id,email,...}` for its account; `{signedIn:false,...}` anonymously |
| Duplicate signup | Existing email, new generated password | Original password still signs in; duplicate input does not replace it |
| `POST /api/wardrobe` | JSON `{facts:{name,category,color,size,fit,owned:true,available,weather,dressCode},consent:true,image}` where `image` is base64 JPEG bytes | 2xx garment record with stable `id`, nested confirmed `facts`, `photoConsent:true`, and `photoUrl` |
| Rejected photo | Missing/false consent or damaged image bytes | 4xx; no new wardrobe record |
| `GET /api/wardrobe` | Session cookie | Array of that person's garment records; no records for a new account |
| `GET /api/wardrobe` | No session cookie | 401; no wardrobe records |
| `GET /api/wardrobe/:id/photo` | Owner session | Actual decodable image, at least 100 pixels per side, visually matching the uploaded shirt after resizing or re-encoding |
| `PATCH /api/wardrobe/:id` | Owner session and flat confirmed-facts JSON object | Updated garment record; another user's or anonymous session cannot read, update, delete, list, or retrieve its photo |
| `DELETE /api/wardrobe/:id` | Owner session | Removal; another user's or anonymous session cannot read, update, delete, or retrieve its photo |
| `POST /api/wardrobe/outfit` | `{occasion:"dinner",weather:"mild",dressCode:"smart-casual"}` | `{kind:"complete",items:[...],explanation,...}` when a complete owned set is supported |
| Missing outfit facts | One of `weather:"unknown"` or `dressCode:"unknown"` | A nonempty `context-question` for that fact, or an `incomplete` abstention with a nonempty explanation; no outfit items |

Every complete outfit has top, bottom and footwear categories. Every suggested record is in the wearer's collection, owned, available, confirmed to fit, and has weather and dress-code facts matching the known request. The checker saves a matching complete set plus available distractors that are unfit, unavailable, or incompatible with the request, and rejects any such distractor in the result. A complete result cannot contain suggested or unowned items.

With only one owned shirt, or when weather or dress code is unknown, the API asks one question or abstains without an outfit. The checker requires the public question to identify the missing fact, or requires a nonempty abstention explanation. Its complete-set proof uses three licensed real image fixtures, reusing those fixtures for fact variations; the browser journey separately proves the one-shirt alternative. It checks factual constraints, not fashion quality or ranking.

The checker reads a garment through the owner's wardrobe collection and photo URL; it does not assume a per-item GET route. No exact inference label, internal database structure, component name, scoring implementation or model provider is asserted. A future transport change must be reconciled against public browser/API behavior while retaining the same requirement outcomes and their bad-variant proofs.

## Zero-garment starter-plan precursor

The user-facing scope, workflow, allocation rules, and external-link disclosures are owned by [Build my wardrobe](../../README.md#build-my-wardrobe).

The starter-plan API stays inside the authenticated wardrobe boundary:

| Interface | Request | Observable response |
| --- | --- | --- |
| `GET /api/wardrobe/starter-plans` | Existing private session | Only that account's saved plans, including input, role states, allocations, and status |
| `POST /api/wardrobe/starter-plans` | Input accepted by [starterSaveSchema](../../shared/starter-plan.ts), including optional edited needs | A saved active text plan with the complete selected roles, role allocations, edited need text, and persisted timestamps |
| `PATCH /api/wardrobe/starter-plans/:id` | Action accepted by [starterPlanActionSchema](../../shared/starter-plan.ts) | Owner-scoped update; a replacement marks the prior plan replaced, a rejection remains in history, and ownership confirmation leaves the owned wardrobe unchanged |

Each plan accepts one occasion string and weather values `warm`, `mild`, `cold`, or `unknown`. Warm does not imply dry weather. The capsule combines pieces into several looks for that same occasion, with a planning budget share per piece. The browser derives the capsule pieces and looks from the saved input and role states. Role combinations and request validation are defined in [the starter-plan schemas](../../shared/starter-plan.ts). The checker verifies that allocations follow the README's rules. The starter-plan browser regressions also verify zero allocation when all roles are confirmed owned. An attempt to mutate a replaced or rejected saved plan returns 409. Requests that fail schema validation return 400, another account's plan ID returns 404, and anonymous requests require authentication.

The production browser case starts from the public entry, completes signup, confirms the empty collection, enters and saves an occasion plan by keyboard, inspects unknown facts and budget arithmetic, exercises a failed replacement and retry, reloads, replaces a need, confirms existing ownership, replaces and rejects plans, and checks the zero-budget outcome. It verifies the collection remains empty throughout, generic links contain no private context, phone and desktop layouts do not overflow, and no external request occurs before an explicit link action. Invalid outfit-role combinations are refused. The test suite retains its current privacy, consent, contrast, account, and owned-outfit checks.

The independent good and deliberately broken controls reject fake in-stock or delivery claims, wrong allocation totals, contradictory outfit/ownership constraints, and planned-role leakage into the owned collection. The production suite also verifies the new account export contains saved starter plans; account deletion removes plans through the existing user ownership boundary.

## India shopping links

The user-facing scope and disclosures are owned by [Build my wardrobe](../../README.md#build-my-wardrobe); the verified source and its rights record are in [Shopping sources](../../docs/shopping-sources.md).

Scope decision: this slice ships retailer section links only. There is no product feed or image right, so it selects no individual garments and shows no prices, photos or copied product text. The complete explained outfit for a zero-garment shopper is the starter plan capsule that is already merged; the shopping links sit beside it.

| Interface | Request | Observable response |
| --- | --- | --- |
| `GET /api/wardrobe/shopping-sources` | Existing private session | Array of sources. Each has `region.country` `IN`, `currency` `INR`, a `rights` record with boolean `productFacts`, `prices` and `images`, an `affiliate` record naming its `redirectHost` and `channelId`, and `destinations` with `url` and `affiliateUrl` |
| `GET /api/wardrobe/shopping-sources` | No session | 401, 403 or 404 |

Every destination `url` is HTTPS on the source's `retailerHost`. Every `affiliateUrl` is HTTPS on the affiliate `redirectHost` and carries exactly `cid`, `source` and `url` parameters: `cid` is the approved channel and `url` is the destination. No other tracking field may be added.

The production browser case signs up, plans a warm casual outfit in INR with footwear already owned, and requires no shopping link before a retailer department is chosen. After choosing the men's department, it requires exactly two approved affiliate links (top and bottom), each marked sponsored, opening a separate page, labeled as an affiliate link, and free of plan or account details. Each has a matching ordinary retailer link. A visible commission disclosure sits above and near the first link at phone width. The section shows no product images. When the source has no image or price rights, it explains that photos and prices are not shown. It states that the checkout total is unknown, makes no stock, delivery or within-budget claim, and shows no money amounts other than the ceiling and planning shares. No external request occurs before a link is opened. Opening one link reaches exactly its affiliate destination with no referrer. A formal plan and a USD plan get no affiliate links. Automated WCAG AA scans pass at 390px and 1440px with no horizontal overflow, the owned wardrobe stays empty, and the journey has no browser errors. Contract stubs check only the API boundary; known-bad variants add a private tracking field or redirect away from the named section.
